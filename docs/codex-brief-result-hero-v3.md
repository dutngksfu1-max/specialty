## 3. 요구사항 6가지

### 3.1 카드를 더 세분화하고, 히어로를 살짝 키웁니다

지금은 한 덩어리입니다. 안쪽을 **역할이 다른 면들로 쪼개 주세요.**
정체성(코드·이름·캐릭터) / 밸런스(인포그래픽) / 서술(리듬)이 서로 다른 무게로 읽혀야 합니다.

- 몇 조각으로 나눌지, 어떤 그리드인지는 **당신이 정합니다**
- 카드 안 카드는 **1단계까지만** 허용합니다 (3단계 중첩 금지 — `AGENTS.md` 4장)
- 크기는 "살짝" 키웁니다. 첫 화면에서 코드·이름·캐릭터까지는 스크롤 없이 보여야 합니다

### 3.2 4렌즈 코드를 주인공으로 세웁니다

알파벳 4글자입니다. 예: `GARM`, `DOCL`.

| 자리 | 축 | positive | negative |
|:--:|---|---|---|
| 1 | 힘을 얻는 방향 | 교류형 **G** (Gather) | 몰입형 **D** (Dwell) |
| 2 | 먼저 눈에 들어오는 것 | 실제형 **A** (Actual) | 가능성형 **O** (Outlook) |
| 3 | 판단할 때 먼저 살피는 것 | 원칙형 **R** (Rule) | 맥락형 **C** (Context) |
| 4 | 일을 굴리는 리듬 | 계획형 **M** (Map) | 유연형 **L** (Live) |

**요구**

- 코드는 히어로에서 **유형 이름 다음으로 큰 요소**여야 합니다
- 네 글자를 **각 자리별로 분해해 읽을 수 있어야 합니다.** 글자만 크게 띄우고 끝내지 마세요
  → `교류 G · 실제 A · 원칙 R · 계획 M` 같은 해설이 코드에 붙어 있어야 합니다
- **균형 자리는 `·` 로 비웁니다.** 예: `G·RM`
  이때 "두 번째 자리는 어느 한쪽으로 기울지 않아 한 글자로 적지 않았어요" 취지의 안내가 함께 보여야 합니다
  (문구 자체는 데이터로 들어옵니다 — 4장 참조)
- 균형 자리가 있어도 **코드는 항상 표시합니다.** 숨기지 마세요

### 3.3 유형별 캐릭터 16종 — 5장 참조

### 3.4 "나온 유형 요소 설명" 블록

코드 네 글자가 각각 무엇을 뜻하는지, 그리고 **그게 이 사람에게 어떻게 나타나는지** 를 히어로 안에서 읽을 수 있어야 합니다.

- 글자 · 극 이름 · 그 축의 한 줄 서술이 한 세트입니다
- 축별 한 줄 서술은 이미 데이터로 들어옵니다 (`narrative.axes[].reading.rhythm`)
- 4장 전부를 같은 크기로 늘어놓으면 다시 단조로워집니다. **강한 축과 균형 축의 무게를 다르게** 주세요

### 3.5 히어로 요약 분량 늘리기

지금은 `oneLiner` 한 줄 + `rhythm` 한 문단입니다. **새 문구를 지어내지 마세요.** 대신 이미 계약에 있는데 히어로에서 안 쓰고 있는 것들을 끌어올리세요.

- `narrative.axes[].reading.headline` / `.summary` — 축별 짧은 문장 4쌍
- `ranking` — 네 관점 중 무엇이 도드라지는지
- 아래 본문 섹션과 **중복 노출은 피합니다.** 히어로가 요약이고 본문이 상세여야 합니다

### 3.6 시각적으로 더 밀어붙이기

현재 히어로는 안전하지만 밋밋합니다. 강화하되 **금지 패턴은 그대로입니다** (8.4장).

허용되는 강화 수단:

- 면 분할과 색면 대비 (`primary-soft` / `surface` / `surface-inset`)
- 선화 요소, 인덱스 탭, 모서리 표식, 어긋난 보조 면 (`design.md` 5.4)
- 타이포 스케일의 과감한 점프 (`text-display-lg` 위로 갈 필요가 있으면 토큰을 먼저 추가)
- 캐릭터와 인포그래픽 자체의 존재감

## 4. 데이터 계약 — 무엇이 들어오는가

### 4.1 중요: 순서

**4렌즈 코드의 엔진·콘텐츠 작업은 이 문서 작성자가 먼저 끝내 둡니다.**
당신이 시작할 시점에는 아래 값이 이미 `ResultRenderer`에서 사용 가능합니다.
**직접 계산하지 마세요. 축 점수를 보고 글자를 조립하는 코드를 `features/`에 쓰면 안 됩니다.**

```ts
// src/domain/assessment/result/typeCode.ts — 동기 순수 함수
buildTypeCode(
  definition.axes,
  snapshot.score.axisScores,
  narrative.balancedAxisIds,
  definition.typeCode,
): TypeCode | null
// →
{
  code: string                 // "GARM" | "G·RM"
  slots: readonly {
    axisId: AxisId
    letter: string             // "G" | "·"
    poleSide: "positive" | "negative" | null   // 균형이면 null
    poleLabel: string | null                   // "교류형" | null(균형)
    isBalanced: boolean
  }[]
  hasBalancedSlot: boolean
  crosswalkCode: string | null // 균형 자리가 있으면 null
}
```

표기 문구는 `definition.typeCode` 에 들어 있습니다 (`TypeCodeSpec`).

| 필드 | 쓸 곳 |
|---|---|
| `label` | 체계 이름 — `"4렌즈 코드"` |
| `balancedNote` | 균형 자리가 있을 때 코드 옆 안내 |
| `crosswalk.summaryLabel` | 접힘 토글 문구 |
| `crosswalk.systemLabel` | 펼쳤을 때 환산 코드 앞 이름 |
| `crosswalk.disclaimer` | 근사임을 알리는 문구. **반드시 함께 표시** |
| `crosswalk.unavailableNote` | `crosswalkCode`가 null일 때 대신 보여 줄 문구 |

**함수가 `null`을 돌려줄 수 있습니다** (콘텐츠가 코드 규격을 주지 않은 검사). 이때는 코드 영역 전체를 생략하고, 나머지 히어로는 정상 동작해야 합니다.

글자는 **콘텐츠가 소유합니다.** `AxisPole.code` 로 주입됩니다. 축 id나 글자를 `features/` 에 하드코딩하면 다음 검사에서 화면이 깨집니다.

### 4.2 기존 값 (선행 브리프 2장과 동일)

| 값 | 뜻 | 범위 |
|---|---|---|
| `snapshot.score.axisScores[].rawScore` | 연속 점수 | **−24 ~ +24** |
| `snapshot.score.axisScores[].normalized` | 시각화용 | 0 ~ 1 |
| `snapshot.score.axisScores[].isBalanced` | 정확히 0점인가 | boolean |
| `narrative.balancedAxisIds` | **균형 구간 축들** (절댓값 5 이하) | `Set<AxisId>` |
| `narrative.axes[].reading.intensityBandId` | 강도 | `balanced`/`leaning`/`clear`/`strong`/`defining` |

> `AxisScore.intensityBandId` 는 저장된 낡은 값입니다. **쓰지 마세요.**
> 강도는 항상 `narrative.axes[].reading.intensityBandId` 를 쓰세요.

### 4.3 MBTI 환산 — 접힘 상태가 기본

법적으로 조심할 영역입니다. **다음을 정확히 지켜 주세요.**

- 기본 상태는 **접혀 있어야 합니다.** 사용자가 열어야 보입니다
- 히어로 최상단이 아니라 **히어로 하단 또는 코드 블록 끝**에 둡니다
- 4렌즈 코드보다 **작아야 합니다.** 같은 크기로 나란히 두지 마세요
- 네 글자를 소스에 통째로 적지 마세요. 조립은 엔진이 끝내서 `crosswalkCode` 로 넘겨줍니다
- `<details>/<summary>` 또는 동등한 키보드 접근 가능 토글을 씁니다
- `crosswalk.disclaimer` 를 **반드시 함께** 표시합니다. 근사라는 사실을 감추지 않습니다
- **`crosswalkCode` 가 `null` 이면 환산을 만들어 내지 마세요.** 균형 자리가 있어 한쪽으로
  단정할 수 없다는 뜻입니다 (DEC-046). `crosswalk.unavailableNote` 를 대신 보여 줍니다

## 5. 캐릭터 16종 — 제작 규격

### 5.1 무엇을 만드는가

16개 유형 각각에 대응하는 **정지 일러스트 1종씩, 총 16개.** SVG.

### 5.2 조형 방향은 당신이 정합니다

먼저 **아래를 직접 열어 보고** 방향을 정하세요. 지금 프로젝트의 그림 문법이 거기 다 있습니다.

```
public/assessments/teacher-style/section-01.svg   # ~ 04까지 4개
public/assessments/teacher-style/hero-teaching-journey.webp
src/features/result/TypeEmblem.tsx
docs/type-emblem.md
docs/design.md  3장(색) · 5.4(카드 덱 문법) · 13장(금지 패턴)
```

현재 선화 문법에서 읽히는 것 (참고용이며, 이대로 하라는 뜻은 아닙니다):

- stroke `#506856` (sage 계열), `stroke-width` 1.75, `stroke-linecap="round"`
- 채움은 최소한. 작은 면에 `#E5C58E`(웜 오커) · `#BCC9B9`(세이지 라이트) 정도
- viewBox `0 0 160 112`, 물결 지면선 위에 오브제 하나
- 얼굴·표정 없음. 사물과 풍경의 은유

**당신이 결정할 것**: 인물 실루엣인가, 사물 은유인가, 풍경인가, 도구·교실 오브제인가.
16종이 **한 세트로 보이면서 서로 구별되는** 방법도 당신이 설계합니다.
(예: 공통 무대 + 요소 4개 조합 / 공통 실루엣 + 자세·소품 변주 / 공통 구도 + 오브제 교체 — 무엇이든)

### 5.3 반드시 지킬 것

| 지킬 것 | 이유 |
|---|---|
| **귀엽게 만들지 않습니다.** 큰 눈·볼터치·과장된 머리 비율·둥근 마스코트 금지 | 사용자는 초등교사입니다. 아이용 캐릭터로 읽히면 검사의 신뢰가 깎입니다 |
| **차분한 성인 톤.** 절제된 선, 조용한 색 | 현재 디자인의 인상과 이어져야 합니다 |
| **색만으로 16종을 구분하지 않습니다.** 형태가 달라야 합니다 | 색각 이상 사용자에게 정보가 사라집니다 (`AGENTS.md` 5장) |
| **성별·연령·인종이 특정되지 않게** 합니다 | 모든 선생님이 자기 것으로 받아야 합니다 |
| **금지 표현 없음.** 파일명·`id`·주석·`alt` 어디에도 기존 성격유형 검사 4글자 코드나 그 명칭을 쓰지 않습니다 | `AGENTS.md` 1.1. 파일명은 4렌즈 코드를 쓰세요 (`garm.svg`) |
| **외부 이미지·폰트·CDN 요청 0건** | 오프라인(PWA)에서 결과가 깨지면 안 됩니다 |


### 5.5 배치 규칙

- 균형 자리가 하나라도 있으면 **16종 캐릭터 대신 `balancedArtwork`** 를 씁니다
  (한쪽 방향으로 단정하지 않는다 — DEC-046)
- 캐릭터는 장식이 아니라 **정보**입니다. `alt` 는 비우고(`alt=""`), 옆 텍스트가 의미를 전달하게 하세요
- 360px에서 캐릭터가 화면을 다 잡아먹지 않아야 합니다. 폭에 따라 크기가 줄거나 배치가 바뀝니다
- 기존 `TypeEmblem` 과 **함께 두 개를 다 보여 주지 마세요.** 같은 정보의 중복입니다. 흡수하거나 하나를 버리세요

## 6. 밸런스 인포그래픽 규격

### 6.1 무엇을 보여 주는가

네 축의 기운 정도를 **한 그림으로** 봅니다. 지금 축 카드의 발산 막대 4개는 본문에 그대로 두고, 히어로에는 **전체 형태가 한눈에 들어오는 요약**을 놓습니다.

### 6.2 형태는 당신이 정합니다

참고할 두 방향 (다른 안을 내도 됩니다):

**안 1 — 4스포크 레이더 (사각형)**
축 4개 = 꼭짓점 4개. 길이는 점수의 절댓값. 방향은 색·라벨로 구분.
장점: 단순, 사각형 실루엣이 유형마다 다름. 단점: **방향 정보가 형태에서 사라집니다.**

**안 2 — 8스포크 레이더 (팔각형)**
극 8개 = 꼭짓점 8개. 마주 보는 두 극 중 기운 쪽만 뻗습니다.
장점: 방향과 강도를 형태 하나로 읽습니다. 각 꼭짓점에 **4렌즈 글자를 그대로 라벨링**할 수 있어 코드와 그림이 이어집니다.
단점: 8개 라벨의 모바일 조판이 까다롭습니다.

> 개인적으로는 안 2가 4렌즈 코드와 맞물려서 좋아 보이지만, **최종 판단은 당신 것입니다.**

### 6.3 반드시 지킬 것

- **색만으로 방향을 전달하지 않습니다.** 축 이름·극 라벨·수치 또는 형태를 함께 답니다
- 색은 `design.md` 3.4의 **검증 완료 토큰만** 씁니다. 눈대중으로 새 색을 만들지 마세요
  - 네 축을 한 그림에 겹칠 때: `chart-overlay-1~4` (`#00682e` · `#da950b` · `#ae4090` · `#2580c1`)
  - 방향: `chart-negative #00713e` / `chart-positive #c06f0a` / 균형 `chart-neutral sand-300`
- **균형 축을 0으로 그리지 마세요.** 찌그러진 도형이 "부족함"으로 읽힙니다.
  균형 구간은 중앙 부근의 넓은 띠·패턴으로 표현하고 균형 라벨을 답니다 (`design.md` 9.1)
- **등급·순위·백분위처럼 읽히면 안 됩니다.** 넓은 도형이 "좋은 것"으로 보이지 않게 하세요.
  필요하면 "크다=좋다가 아니라 뚜렷하다는 뜻" 취지의 안내를 답니다
- 스크린리더용 대체 표현을 제공합니다 (`<title>`+`<desc>` 또는 시각적으로 숨긴 목록)
- 360px에서 라벨이 겹치거나 잘리지 않아야 합니다. 필요하면 그림 밖 범례로 내리세요

## 7. 아키텍처 — 여기서 실수하면 되돌려야 합니다

`AGENTS.md` 7장: **새 검사를 추가할 때 `domain/` `application/` `features/` `app/` `components/ui/` 는 0줄 수정이어야 합니다.**

| 하지 마세요 | 대신 |
|---|---|
| `features/` 에 `resultKey`/`axisId` 별 `switch`·객체 리터럴 | 데이터로 주입받아 순회 |
| `features/` 에 16개 SVG 인라인 | `public/` + `presentation.ts` 참조 |
| 글자 `"G"` 를 컴포넌트에 하드코딩 | `AxisPole.code` 사용 |
| 축이 4개라고 가정한 그리드 | `definition.axes.length` 로 대응. 4개가 아니어도 죽지 않아야 합니다 |
| 채점·코드 조립 함수를 `async` 로 | 동기 순수 함수 |
| `domain/` 에 react·svg·window import | 금지 |

`presentation.ts` 에 필드를 늘리면 **`src/infrastructure/content/contentPackageSchema.ts` 의 Zod 스키마도 같이 늘려야 합니다.** 안 그러면 콘텐츠 로딩이 실패합니다.

## 8. 디자인·접근성 (협상 불가)

### 8.1 토큰

색·간격·반경·폰트는 **토큰으로만.** 없는 값이 필요하면 `docs/design.md` 에 **먼저 추가한 뒤** 씁니다.
`radius-full` 은 라디오 원과 진행바 전용입니다. 카드·뱃지는 `radius-lg`(18px) / `radius-xs`(6px).

### 8.2 반응형

360 · 390 · 768 · 1024 · 1440px, 세로·가로 회전, **200% 확대**에서 확인합니다.
**360px에서 가로 스크롤 0.** 캐릭터·인포그래픽·코드 뱃지 셋 다 해당됩니다.

### 8.3 접근성

- 코드 뱃지는 스크린리더에서 글자 나열이 아니라 **의미로 읽혀야** 합니다 (`aria-label` 또는 시각적 숨김 텍스트)
- MBTI 환산 토글은 키보드로 열고 닫힙니다. `focus-visible` 유지
- 인포그래픽에 대체 표현 필수
- 캐릭터에 애니메이션을 넣는다면 `prefers-reduced-motion` 존중
- 본문 대비 4.5:1, 터치 타깃 44×44px

### 8.4 금지 패턴 (그대로 유효합니다)

보라/파랑 gradient · sparkle 남발 · glassmorphism · floating blob · 모든 요소 pill ·
지나치게 둥근 카드 · **카드 안 카드 안 카드** · 과도한 emoji · **유아적 학교 캐릭터** ·
의미 없는 decoration · **색만으로 상태 전달** · focus outline 제거 · "궁합" 표현 ·
결과에 등급·순위·백분위 · 직업 추천

### 8.5 문구 규칙

새 문구를 지어낼 일이 있으면 (버튼·안내 등):

- "당신은 ~형입니다" ❌ → "~하는 편이에요 / ~할 때가 많아요" ✅
- 낙인이 되는 말 금지 ("게으른", "우유부단한")
- 한국어 존칭
