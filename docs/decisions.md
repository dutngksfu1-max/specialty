# Decisions — 클래스렌즈

> 문서 상태: v0.2
> 최종 수정: 2026-08-20
> 이 문서는 **모든 중요 결정의 기록**입니다. 결정이 바뀌면 새 DEC를 추가하고 이전 항목에 `SUPERSEDED`를 표시합니다.

## 이 문서를 쓰는 이유

나중에 "왜 이렇게 만들었지?"라는 질문이 반드시 나옵니다.
그때 코드를 뒤지는 대신 이 문서를 보면 되도록, **결정과 그 이유를 함께** 남깁니다.

## 상태 값

| 상태 | 뜻 |
|---|---|
| `CONFIRMED` | 사용자가 승인함. 구현 진행 가능 |
| `DEFAULT` | 저(Claude)가 기본값으로 정함. 사용자가 언제든 바꿀 수 있음 |
| `WAITING` | 사용자 결정 대기 중. **이 결정에 종속된 구현을 시작하지 않음** |
| `SUPERSEDED` | 다른 DEC로 대체됨 |

## 사용자 승인이 반드시 필요한 항목 (임의 결정 금지)

- 서버 저장 도입 / 개인정보 서버 전송 / Supabase 실제 연결
- scoring cutoff / tie-break / compatibility logic
- navigation 구조 변경 / branding
- architecture contract 변경 / 대형 dependency 추가
- PRD에 없는 기능 추가

## DEC-001

**Question:**
축 점수가 정확히 0점일 때(동점) 어떻게 처리하는가?
축당 10문항 × 중앙값 변환 구조에서는 0점이 반드시 발생할 수 있다.

**Options:**
A. 연속 점수는 보존하고, 0인 축은 결과 화면에 '균형'으로 표시. 프로필 매핑은 콘텐츠에 미리 정의한 `defaultPole`로 확정
B. 0인 축이 있으면 두 방향의 프로필을 함께 소개(주 프로필 + 곁 프로필)
C. 해당 축 문항 중 극단 응답(1점·5점) 강도가 큰 쪽으로 판정

**Recommendation:**
A. 결과가 항상 하나로 확정되어 재현 가능하고 구현이 단순하다.
B는 축 2개가 0이면 프로필이 4개로 늘어 결과 화면과 콘텐츠 분량이 급증한다.
C는 검증 근거가 없고 사용자에게 설명하기 어렵다.

**Decision:**
`CONFIRMED` — A (2026-08-19)

**Owner:** User

**Implementation note:**
- `AssessmentAxis.defaultPole` 필드가 콘텐츠 패키지에 필수
- `AxisScore.isBalanced = (rawScore === 0)`
- 화면: 마커 정중앙 + '균형' 배지 + 양쪽 pole 라벨을 동등한 톤으로 표시(한쪽 강조 금지)
- `rawScore` 0은 결과 스냅샷에 그대로 저장 (defaultPole로 덮어쓰지 않음)

## DEC-002b

**Question:**
DEC-002에서 3구간을 채택했다. 경계값을 얼마로 할 것인가?
한 축은 10문항이므로 점수 범위는 -20 ~ +20이다.

A. 세 구간이 비교적 고르게 나뉘어 강의장에서 다양한 결과가 나온다.

**Decision:**
`CONFIRMED` — A (2026-08-19)

**Owner:** User

**Implementation note:**
- 경계값은 **코드가 아니라 콘텐츠 패키지 데이터**(`intensityBands`)로 관리한다
- 축마다 다른 값을 쓸 수 있고, 검사마다도 다를 수 있다
- 검증: `intensityBands`가 0부터 최대 절대값까지 빈틈·겹침 없이 덮는지 로드 시 확인

## DEC-007

**Question:**
PWA(설치·오프라인)를 어떤 방식으로 구현할 것인가?

**Options:**
A. `@serwist/turbopack` (Turbopack 공식 지원, Workbox 계열 검증된 캐싱 전략)
B. `@serwist/next` (webpack 플래그가 필요할 수 있음)
C. 라이브러리 없이 Service Worker 직접 작성

**Recommendation:**
A. Next.js 16은 Turbopack이 기본 번들러다. C는 캐시 무효화·업데이트 처리에서 버그가 나기 쉬운 영역이라,
"오프라인에서 검사 유지"라는 핵심 요구사항을 위태롭게 한다.

**Decision:**
`CONFIRMED` — A (2026-08-19)

**Owner:** User

**Implementation note:** (Phase 5에서 구현하며 보강)
- 캐싱 전략은 `docs/architecture.md` 9.3 표를 따른다
- 사용자 응답은 절대 SW 캐시에 넣지 않는다 (IndexedDB가 원본)
- 새 SW 감지 시 자동 새로고침 금지 — 검사 도중 응답 유실 위험
  → `skipWaiting: false` + 인라인 안내("검사를 마친 뒤 새로고침해 주세요") + 사용자가 누를 때만 갱신
- `reloadOnOnline={false}` — 기본값(true)이면 네트워크가 돌아올 때 페이지를 자동 새로고침합니다.
  강의실 와이파이가 끊겼다 붙는 동안 검사 화면이 바뀌면 안 되므로 껐습니다
- **함께 필요한 패키지**: `esbuild`(윈도우) / `esbuild-wasm`(그 외). `@serwist/turbopack`이
  SW를 esbuild로 묶는데, OS에 따라 기본값이 달라 둘 다 devDependency로 설치했습니다.
  `pnpm-workspace.yaml`의 `allowBuilds`에 `esbuild: true`가 필요합니다

## DEC-037

**기존 성격유형 검사의 명칭·유형 코드를 노출할 것인가**

`CONFIRMED` — **A(명칭도 코드도 노출하지 않음)**. 2026-08-20 사용자 승인.

### 배경

"교사 ○○"처럼 잘 알려진 검사 이름을 붙이면 대중성이 크게 올라간다는 요구가 있었습니다.
실제로 그런 이름을 붙여 배포하는 사례도 많습니다. 조사 결과는 이렇습니다.

- 해당 명칭은 **등록상표**이고, 국내 판권사가 존재합니다
- 네 글자 유형 코드는 권리자의 공식 상표 목록에 **없습니다**
- 가장 큰 유사 서비스는 **명칭은 쓰지 않고 코드만 쓰는** 방식으로 분쟁을 피하고 있습니다

### 왜 그럼에도 A인가

| 이유 | 설명 |
|---|---|
| 시장이 정면으로 겹칩니다 | 판권사가 **학교·교육청 대상 연수**를 실제로 판매합니다. 상표권 판단의 핵심은 "같거나 비슷한 서비스에 썼는가"입니다 |
| 상업적·공개적 사용입니다 | 이 제품은 강사가 강의료를 받는 연수에서 쓰입니다. 개인 블로그 밈 테스트와 노출 수준이 다릅니다 |
| 신뢰도 위험이 더 큽니다 | 연수 참가 교사 중 정식 자격 보유자가 한 명만 있어도 그 자리에서 문제가 됩니다. 소송보다 이쪽이 빠르고 치명적입니다 |
| 제품 정직성 | 우리 문항은 교직 장면으로 새로 쓴 것이라 공식 검사와 결과가 다를 수 있습니다. 코드를 붙이면 지킬 수 없는 약속이 됩니다 |

### 대중성은 이렇게 확보합니다

명칭·코드가 아니라 **고유한 결과 제목 + 유형 엠블럼(DEC-039) + 4축 막대그래프**로 확보합니다.
유사 서비스의 대중성도 실은 코드가 아니라 이 세 가지에서 나옵니다.

### 결과

`AGENTS.md` 1.1의 절대 규칙을 **그대로 유지**합니다.
`realContent.test.ts`와 `contentPackageSchema.ts`의 금지 표현 검사도 그대로 둡니다.

`CONFIRMED` — `src/assets/fonts/`. 2026-08-20 (Phase 6 성능 정리).

`public/fonts/PretendardVariable.woff2`(2MB)가 **아무도 쓰지 않는 채로 프리캐시되고 있었습니다.**

- 결과: **앱 설치 시 쓰지도 않는 2MB를 내려받고 있었습니다**

### 조치

| 파일 | 이동 |
|---|---|
| `PretendardVariable.woff2` | `public/fonts/` → **`src/assets/fonts/`** (빌드 입력 전용, 서빙 안 됨) |
| `OFL.txt` | `public/fonts/`에 **유지** — 라이선스 고지는 공개 접근이 유지되어야 합니다 |

실제 폰트는 `defaultCache`의 `static-font-assets` 런타임 캐시가 첫 사용 시 잡습니다.
오프라인 동작은 그대로입니다.

### 효과

```
Service Worker 프리캐시   3094 KiB  →  1085 KiB   (−65%)
```

### 남은 과제 (DEC-030 ②안)

Pretendard Variable 전체 파일은 여전히 **2MB**입니다.
`font-display: block`(DEC-035)이라 폰트가 도착할 때까지 글자가 보이지 않습니다.
학교 와이파이·모바일에서 첫 화면이 느리다는 신고가 들어오면
**한글 서브셋 전환**(DEC-030의 ②안)을 검토해야 합니다. 지금은 보류합니다.

## DEC-046

**결과 해석의 맥락 비약과 균형 단정을 어떻게 바로잡고, 검증을 어떤 순서로 진행할 것인가**

`CONFIRMED` — **B-1 안전 보정 → C 교사 검증 → B-2 최종 보정** 순서로 진행합니다. (2026-08-20 사용자 승인)

### B-1 즉시 적용

- 기존 점수 계산과 강도 경계는 바꾸지 않습니다.
- `0~4 균형` 구간은 어느 한쪽 프로필로 확정하지 않습니다. 단, 0이 아닌 점수는
  `균형 범위에서 ○○ 쪽에 조금 가까움`으로 작은 기울기를 함께 보여 줍니다.
- 정확히 0점일 때에만 양쪽 점수가 같다고 설명합니다.
- 결과 제목·한 줄 설명·교직 리듬은 16개 고정 프로필만 읽지 않고, 축별 방향과 강도 구간으로 조립합니다.
- 교직 리듬은 네 축을 한 문장씩 설명하는 네 문장으로 구성합니다.
- 측정하지 않는 내용에 관한 해석 경계는 본문에서 반복하지 않고 짧은 참고 문구로 한 번만 분리합니다.
- 동료와 나누거나 혼자 회복하는 방식은 학생 대상 말수로 확대하지 않습니다.
- 유연한 운영 방식은 마감을 미루는 습관으로 확대하지 않습니다.
- 균형 축이 하나라도 있으면 방향 조합 엠블럼을 숨기고, 해당 축이 들어간 조합 해석도 보여 주지 않습니다.
- 균형 축이 하나라도 있으면 부호로 선택된 16개 프로필의 장면·협업·행동 문구 대신 균형 전용 중립 안내를 보여 줍니다.
- `축이 함께 움직일 때` 같은 추상 표현을 실제 장면 중심의 말로 바꿉니다.
- 결과를 보장하는 문장을 관찰 가능한 행동과 가능성 표현으로 낮춥니다.

### C 검증

- 실제 교사가 문항을 어떻게 바꿔 말하고 어떤 장면을 떠올리는지 인지 인터뷰로 확인합니다.
- 유연성/미루기, 회복/말수, 구체성/계획성처럼 섞일 수 있는 문항을 우선 검토합니다.
- 익명 파일럿 응답으로 문항 분포·축 내 관계·축 사이 상관·축 구조를 확인합니다.
- 인터뷰·파일럿 원자료는 서버로 보내지 않고 로컬에서만 다룹니다.

### B-2 진입 제한

- 실제 인터뷰와 파일럿 근거 없이 문항 교체, 점수 경계, 동점 처리, 최종 결과 문구를 임의 확정하지 않습니다.
- 경계값이나 동점 규칙을 바꾸려면 별도 DEC와 사용자 승인이 필요합니다.
- 검증 절차와 진입 조건은 `docs/content/teacher-style-v1-validation.md`를 따릅니다.

### 버전

- 문항·축·채점값은 그대로이므로 `assessmentVersion`과 `scoringVersion`은 유지합니다.
- 결과 문구와 해석 방식이 바뀌므로 `contentVersion`을 `3.1.0`으로 올립니다.

## DEC-048

**결과의 해석 폭을 넓히기 위해 문항을 40개에서 48개로 늘릴 것인가**

`CONFIRMED` — **48문항(축당 12문항)으로 확장.** 2026-08-21 사용자 승인.

### 배경

`docs/content/teacher-style-v1-audit.md`의 문항 감사에서, 결과 고도화의 핵심 신호인
**맥락 분화(S4)** 를 네 축 중 **`axis-rhythm` 한 축에서만** 쓸 수 있다는 것이 확인되었습니다.

원인은 문항 품질이 아니라 **장면 분포**입니다. 기존 40문항은 "축 사이 겹침 방지"를 목표로
설계되어 축마다 전용 장면군을 썼고, "한 축 안에서 장면을 비교한다"는 요구는 설계 시점에 없었습니다.

### 결정 내용

| 항목 | 이전 | 이후 |
|---|---|---|
| 전체 문항 | 40 | **48** |
| 축당 문항 | 10 | **12** (네 축 모두 동일) |
| 축당 polarity | +5 / −5 | **+6 / −6** |
| Part당 문항 | 10 | **12** |
| 축당 점수 범위 | −20 ~ +20 | **−24 ~ +24** |

**추가한 8문항** — 비어 있던 (장면 × 방향) 칸만 골라 채웠습니다.

| id | 축 | 장면 | polarity |
|---|---|---|---|
| `energy-11` | 힘을 얻는 방향 | `colleague` | −1 |
| `energy-12` | 힘을 얻는 방향 | `self` | +1 |
| `lens-11` | 먼저 보이는 것 | `guidance` | −1 |
| `lens-12` | 먼저 보이는 것 | `colleague` | +1 |
| `decision-11` | 판단 기준 | `admin` | +1 |
| `decision-12` | 판단 기준 | `admin` | −1 |
| `rhythm-11` | 일 굴리는 리듬 | `self` | +1 |
| `rhythm-12` | 일 굴리는 리듬 | `self` | −1 |

### 얻는 것

| 지표 | 40문항 | 48문항 |
|---|---|---|
| S4 가능 축 | 1 / 4 | **4 / 4** |
| 자격 장면 총합 | 4 | **10** |
| S4 문장 후보 | 2 | **16** |
| **장면 프로파일**(새 해석 틀) | 1 | **5** |

**장면 프로파일**은 기존 4축 구조와 직교하는 새 읽기 방식입니다.
축을 세로로 읽는 대신 `수업 / 업무 / 동료 / 생활지도 / 혼자` 다섯 장면에서
**"이 장면에서의 나"** 를 가로로 읽습니다.

### 왜 48인가 (56·64가 아니라)

| 안 | 문항 | S4 | 자격 장면 | 장면 프로파일 | 작성량 |
|---|---|---|---|---|---|
| 현행 | 40 | 1/4 | 4 | 1 | — |
| **채택** | **48** | **4/4** | 10 | **5** | 8개 |
| — | 56 | 4/4 | 13 | 5 | 16개 |
| — | 64 | 4/4 | 14 | 5 | 24개 |

**56은 작성량이 2배인데 장면 프로파일이 5개로 같습니다.** 48에서 효용이 꺾입니다.
완전탐색으로 계산했으며, 축마다 문항 수를 12로 **똑같이** 맞춰 점수 범위가 갈라지지 않게 했습니다.

### 강도 구간 재산정

점수 범위가 ±20 → ±24로 늘어, 경계를 **범위 대비 비율을 유지한 채** 옮깁니다.

| 구간 | 비율 | 40문항(±20) | 48문항(±24) |
|---|---|---|---|
| `balanced` | 0 ~ 20% | 0 ~ 4 | **0 ~ 5** |
| `clear` | 25 ~ 60% | 5 ~ 12 | **6 ~ 14** |
| `strong` | 65 ~ 100% | 13 ~ 20 | **15 ~ 24** |

균형 구간을 비율로 유지한 이유: 이 경계만이 "방향을 단정할지 말지"를 가르는 안전장치입니다(DEC-046).
범위가 늘었는데 `0~4`를 그대로 두면 균형 구간이 상대적으로 좁아져, 약한 근거로 방향을 단정하게 됩니다.

> DEC-047(3구간 → 5구간)은 이 값 위에서 별도로 진행합니다. 5구간은 축별 서술 36개가 함께 필요하므로
> 콘텐츠 작업(PRD Phase C)과 묶어 처리합니다.

### 감수하는 비용

- **`assessmentVersion` 3 → 4.** 기존에 검사를 마친 분은 **재검사해야** 결과를 봅니다
- 검사 시간 약 10분 → **약 12분**
- `estimatedMinutes`가 `5`로 안내 문구(10분)와 어긋나 있던 것을 **12로 맞췄습니다**

> 재검사를 유발하는 변경이므로 결과 화면 개편(PRD v2)과 **한 번에 묶어** 배포합니다.
> 따로 하면 사용자에게 재검사를 두 번 요구하게 됩니다.

### DEC-046 B-2 제한과의 관계

DEC-046은 검증 데이터 없이 **문항 교체**를 금지합니다. 이번 결정은 **교체가 아니라 추가**이고,
기존 40문항의 본문·축·polarity를 **한 글자도 바꾸지 않았습니다.** 기존 문항의 해석은 그대로 유지됩니다.

새 8문항은 기존 작성 규칙(`realContent.test.ts`)을 그대로 통과합니다 —
축 간 어휘 누수·사회적 바람직성·장면 편중·길이·부정문·극단 표현 검사 전부 자동 검증됩니다.

## DEC-049

**결과 유형에 알파벳 코드를 붙이고, 다른 검사로의 환산을 함께 보여 줄 것인가**

`CONFIRMED` — **4렌즈 코드 도입 + 환산은 기본 접힘.** 2026-08-22 사용자 승인.

### 배경

16개 유형에 짧은 손잡이가 없었습니다. 결과 제목("아이를 세심히 살피고 미리 돕는 교실")은
정확하지만 길어서, 동료에게 말하거나 기억하기 어렵습니다.

### 확정 내용

**① 4렌즈 코드** — 축 하나가 한 자리인 알파벳 4글자.

| 자리 | 축 | positive | negative |
|:--:|---|---|---|
| 1 | axis-energy | 교류형 **G** (Gather) | 몰입형 **D** (Dwell) |
| 2 | axis-lens | 실제형 **A** (Actual) | 가능성형 **O** (Outlook) |
| 3 | axis-decision | 원칙형 **R** (Rule) | 맥락형 **C** (Context) |
| 4 | axis-rhythm | 계획형 **M** (Map) | 유연형 **L** (Live) |

**여덟 글자 모두 기존 성격유형 검사가 쓰는 글자를 피했습니다.** 겹치지 않게 고른 이유는 두 가지입니다.

- 우리 `M`(계획)이 그쪽 글자와 뜻이 정반대인 자리가 있어, 겹치면 사용자가 반대로 읽습니다
- 겹치지 않으면 16조합 중 어떤 것도 금지 패턴을 만들 수 없습니다. 규칙 위반이 **구조적으로 불가능**해집니다

**② 균형 자리는 `·`** — 균형 구간(절댓값 5 이하)인 자리는 글자 대신 가운뎃점을 넣습니다 (`G·RM`).
숨기지 않고 비워 두는 쪽을 골랐습니다. 코드는 항상 보이면서도 단정하지 않습니다 (DEC-046과 같은 원칙).

**③ 환산 표기는 기본 접힘** — 사용자가 열어야 보이고, 4렌즈 코드보다 작게 둡니다.
**균형 자리가 하나라도 있으면 환산하지 않습니다.** 한쪽으로 단정할 수 없는 자리를 억지로
한쪽으로 적는 것은 DEC-046을 정면으로 어기는 일이기 때문입니다.

### 왜 접어 두는가

환산 대상 검사명은 타사 등록상표입니다. 기능은 그대로 제공하되 노출 면적을 줄여,
결과 화면의 주인공이 4렌즈 코드로 남게 했습니다. "아류"로 읽히면 검사 자체의 신뢰가 깎입니다.
근사임을 알리는 문구(`disclaimer`)를 함께 표시합니다.

### 구현 계약

- 글자는 **콘텐츠가 소유**합니다 — `AxisPole.code` / `AxisPole.crosswalkCode` (각 한 글자)
- 표기 규격도 콘텐츠 — `AssessmentDefinition.typeCode` (`TypeCodeSpec`)
- 조립은 **동기 순수 함수** `buildTypeCode()` — `src/domain/assessment/result/typeCode.ts`
- 환산 글자를 네 개 이어 붙인 문자열은 **소스 어디에도 없습니다.** 극마다 한 글자씩만 두고 화면에서 조립합니다
  → 저장소 전체 금지 표현 grep이 계속 **0건**으로 유지됩니다
- 로드 시 Zod가 검사: 글자 한 글자 여부 · 8개 전부 존재 · 중복 없음 · 균형 글자와 충돌 없음

### AGENTS.md 1.1 예외

`AxisPole.crosswalkCode`(한 글자)와 `TypeCodeSpec.crosswalk`(접힌 UI 문구) **두 곳에서만**
환산 표기를 허용합니다. 나머지 모든 사용자 노출 문자열은 기존 금지 규칙 그대로입니다.
`contentPackageSchema.ts`의 `userFacingStrings` 검사 목록에 이 두 필드를 넣지 않는 방식으로 구현했습니다.

## DEC-052

**균형 구간을 어디까지로 볼 것인가**

`CONFIRMED` — **균형은 정확히 0점 하나뿐.** 2026-08-23 사용자 승인.

### 발견된 문제

사용자가 "어떻게 응답하든 네 축이 전부 균형으로 나온다"고 보고했습니다. 확인 결과 **사실이었습니다.**

축 점수는 `정방향 6문항 − 역방향 6문항`입니다. 각 문항이 −2~+2를 내므로
아무렇게나 답했을 때 점수 분포의 **표준편차가 약 4.9점**입니다.
예전 균형 구간 `0~5`는 이 잡음의 ±1 표준편차와 거의 정확히 겹칩니다.
즉 **잡음 구간을 통째로 "균형"이라고 부르고 있었습니다.**

시뮬레이션 결과 (문항·채점 코드 그대로, 응답만 바꿔 측정):

| 응답 유형 | 축 하나가 균형 | 네 축 모두 균형 |
|---|---:|---:|
| 완전 무작위 (10,000회) | **73.2%** | **28.4%** |
| 약한 성향 (강도 0.3) | 84.1% | 49.7% |
| 보통 성향 (강도 0.6) | 18.4% | 0.2% |

문항 키잉(polarity)은 48개 전부 정상이었습니다. 원인은 오직 **구간 폭**이었습니다.

### 확정 내용

| 구간 | 이전 | 변경 | 뜻 |
|---|---|---|---|
| `balanced` | 0 ~ 5 | **0** | 정방향과 역방향이 정확히 맞선 진짜 동점 |
| `leaning` | 6 ~ 10 | **1 ~ 6** | 한 장면에서 보임 |
| `clear` | 11 ~ 14 | **7 ~ 12** | 여러 장면에서 비슷하게 |
| `strong` | 15 ~ 19 | **13 ~ 18** | 장면이 바뀌어도 같은 선택 |
| `defining` | 20 ~ 24 | **19 ~ 24** | 거의 모든 장면에서 |

구간 **id는 그대로**라 결과 서술 문구를 한 줄도 고치지 않았습니다. 경계값만 옮겼습니다.

### 개선 결과

| 응답 유형 | 축 하나가 균형 | 네 축 모두 균형 |
|---|---|---|
| 완전 무작위 | 73.2% → **8.0%** | 28.4% → **0.0%** |
| 약한 성향 (0.3) | 84.1% → **3.8%** | 49.7% → **0.0%** |
| 보통 성향 (0.6) | 18.4% → **0.0%** | 0.2% → **0.0%** |

### DEC-046과의 관계

DEC-046은 "약한 근거로 방향을 단정하지 않는다"는 원칙입니다. 이 결정은 그 원칙을 **버리지 않고 옮깁니다.**

- 방향은 부호가 알려 줍니다 — 0이 아니면 어느 쪽인지 말합니다
- 얼마나 기울었는지는 **구간이** 말합니다 — 1점은 `조금 뚜렷`이지 `매우 뚜렷`이 아닙니다
- 언어 규율(DEC-047)이 그대로 살아 있습니다 — 구간이 올라가도 **확신이 아니라 장면 범위**가 넓어집니다

약한 기울기를 **숨기는 것**이 아니라 **약하다고 말하는 것**이 정직합니다.

### 남은 한계 (알고 감수함)

모든 문항에 같은 값을 찍으면 정·역이 상쇄되어 **반드시 0점**이 됩니다.
이것은 버그가 아니라 묵종 편향을 상쇄하는 설계의 결과이고, 정보가 없는 응답에
방향을 붙이지 않는 편이 옳습니다. `balanceCalibration.test.ts`에 사실로 기록해 두었습니다.

두 번째 한계는 **정방향·역방향 문항이 서로 배타적이지 않다**는 점입니다.
"동료와 이야기하면 힘이 난다"와 "혼자 있는 시간이 필요하다"에 모두 동의하는 사람이 많고,
이때 점수는 0으로 상쇄됩니다. 실제 응답 데이터가 모이면 문항 단위로 검토할 대상입니다
(DEC-046 C단계).

### 회귀 방지

`src/infrastructure/content/balanceCalibration.test.ts` 5개 테스트가
구간 폭·무작위 응답 균형 비율(15% 미만)·약한 성향의 방향 판정을 강제합니다.
사람 눈으로는 잡히지 않는 종류의 회귀라 기계가 지킵니다.

## DEC-054

**결과 캐릭터에 사용자 선택 성별을 반영하고 유형별 남녀 자산을 둘 것인가**

`CONFIRMED` — **닉네임 입력과 함께 남성·여성 캐릭터 성별을 고르고, 총 34종을 사용합니다.** 2026-08-23 사용자 지시.

### 수량

| 구분 | 계산 | 수량 |
|---|---:|---:|
| 방향이 분명한 결과 | 16유형 × 남성·여성 | 32종 |
| 균형 축이 하나라도 있는 결과 | 균형 공통 1종 × 남성·여성 | 2종 |
| 합계 | 32 + 2 | **34종** |

균형 축의 개수나 위치별로 캐릭터를 더 만들지 않습니다. DEC-046에 따라 균형 축이 하나라도 있으면
한쪽 프로필로 단정하지 않고, 선택 성별의 균형 전용 캐릭터 한 종을 사용합니다.

### 입력·저장 규칙

- 랜딩의 닉네임 입력과 같은 참여 영역에서 `남성`·`여성`을 실제 radio로 고릅니다
- 닉네임은 선택 입력이지만 캐릭터 성별은 새 검사 시작에 필요한 값입니다
- 선택값은 채점·유형 결정에 관여하지 않고 결과 캐릭터 조회에만 씁니다
- 닉네임·응답과 마찬가지로 IndexedDB에만 저장하며 서버로 보내지 않습니다
- 세션 시작 시 `characterGender`를 스냅샷으로 남기고, 완료 시 `ResultSnapshot`에도 복사합니다
- DEC-054 이전의 저장 데이터는 값을 추정하거나 지우지 않습니다. `null`로 읽고 캐릭터만 생략합니다

### 표현 규칙

- 남성·여성은 성인 인물의 자연스러운 실루엣·머리·복장에서 알아볼 수 있어야 합니다
- 같은 유형의 남녀는 같은 행동 개념과 핵심 소품을 공유합니다
- 성별에 따라 리더·조력자, 계획·공감 같은 역할을 나누지 않습니다
- 성별 외 연령대·인종은 특정하지 않습니다

## DEC-054

**「교실에서 드러나는 모습」을 어떻게 다시 쓸 것인가**

`CONFIRMED` — **상황 제목 도입 + 문장 구체화 + 사례 확대 + 세 묶음 시각 분리.** 2026-08-23 사용자 승인(선택 C).

### 배경

사용자 지적 네 가지입니다.

1. "~해 볼 수 있어요" 같은 **추측형 어미**라 확신이 없게 읽힌다
2. 추상적이다. **실제 일어날 상황**이나 **교사가 실제 하는 일**을 보고 싶다
3. 확신 없는 말투는 **불쾌감**을 준다. 사례 다양성도 부족하다
4. 처음 보고 **"뭘 얘기하려는 거지?"** 싶었다 — 가독성이 떨어진다

`~할 수 있어요`는 서술이 아니라 제안입니다. 읽는 사람은 자기 이야기를 들은 게 아니라
훈수를 들은 것이 됩니다. 결과 화면이 조심스러운 이유는 **강도를 과장하지 않기 위해서**였는데
(DEC-047 언어 규율), 그게 장면 서술까지 번져 아무 말도 하지 않는 문장이 되어 있었습니다.

> 언어 규율은 **얼마나 확신하는가**를 다루지, **무엇이 일어나는가**를 흐리라는 뜻이 아닙니다.
> 이번 변경은 DEC-047과 충돌하지 않습니다. 강도 주장은 그대로 절제하고, 장면만 또렷하게 적습니다.

### 확정 내용 ① — `SceneNote`에 상황 제목 추가

```ts
interface SceneNote {
  scene: string;      // 수업 / 생활지도 / 업무 / 동료 / 학부모
  situation: string;  // 신규 — 짧은 상황 제목 (2~16자)
  text: string;       // 그 상황에서 실제로 일어나는 일
}
```

전:  `[수업] 다음 주에 필요한 것을 미리 확인해, 수업 중 준비 때문에 멈추는 일을 줄일 수 있어요.`
후:  `[수업] **월요일 1교시** — 금요일 퇴근 전에 다음 주 교구를 챙겨 둡니다. 월요일 아침에는 바로 수업을 시작해요.`

### 확정 내용 ② — 문장 144개 전면 재작성

- 16개 프로필 × 3묶음 × 3개 = **144개** (기존 114개에서 확대)
- 세 묶음 모두 **3개로 통일**. 묶음마다 개수가 다르면 화면 높이가 어긋납니다
- `balancedGuidance`의 9개도 같은 규격으로 교체

### 확정 내용 ③ — 세 묶음을 서로 다른 면으로 분리

예전에는 셋이 한 면 위에 같은 모양으로 이어져, 지금 읽는 것이 강점인지 주의 신호인지
구분되지 않았습니다. **색만으로 나누지 않습니다** — 왼쪽 인덱스 막대의 결이 함께 달라집니다.

| 묶음 | 면 | 인덱스 막대 | 아이콘 |
|---|---|---|---|
| 강점이 드러나는 장면 | 옅은 세이지 | 실선 | check |
| 여유가 줄었을 때 나타나는 모습 | 웜 뉴트럴 | 클레이 사선 | warning |
| 동료와 함께 일할 때 | 흰 면 | 슬레이트 점선 | message |

상황 카드는 3열 격자로 두고, 카드 안에서 `장면 → 상황 제목(굵게) → 본문` 순으로 읽습니다.

### 회귀 방지

`realContent.test.ts`에 세 가지를 추가했습니다.

- **추측형 어미 차단** — `수 있어요` / `수 있습니다` / `것 같아요` / `해 보세요`가 장면 서술에 있으면 실패
- **상황 제목 규격** — 2~16자, 본문과 같으면 실패
- **한 프로필 안 제목 중복 금지** — 같은 제목이 두 번 나오면 실패

### 함께 바뀐 것

`AGENTS.md` 6장의 결과 구성 순서에서 묶음 제목 두 개를 새 제목으로 갱신했습니다.

**렌즈 카드와 밸런스 지도의 정렬·일관성을 어떻게 잡을 것인가**

**① 2-1-1로 어긋남** — 도드라지는 축에 `sm:col-span-2`를 줘서, 네 카드가

**② 카드마다 정보량이 달랐음** — 요약 문단이 도드라지는 축에만 붙어서,

**③ 밸런스 지도의 안내 문구** — "도형의 크기는 좋고 나쁨이 아니라…"가

**② 네 카드가 같은 구조를 갖습니다.** 요약 문단을 전부 표시합니다.

> 나머지 세 관점이 덜 중요한 정보처럼 보입니다. 네 관점은 동등하게 읽혀야 합니다.

**③ 줄바꿈 규칙.** 카드가 좁아지면 제목이 두 줄로 넘어갑니다. 넘어가는 것 자체는

| 속성 | 하는 일 |
|---|---|
| `word-break: keep-all` | 한글을 **어절 단위로만** 끊습니다. 낱말 중간에서 잘리지 않습니다 |
| `text-wrap: balance` (제목) | 두 줄 길이를 고르게 나눕니다. "긴 줄 + 한 단어"를 막습니다 |
| `text-wrap: pretty` (본문) | 마지막 줄에 한 단어만 남는 것을 줄입니다 |

**④ 밸런스 지도 안내 문구 제거.** 화면에서 뺐습니다. 뜻은 SVG `<desc>`가 계속
스크린리더에 전달하므로 접근성은 그대로입니다.

## DEC-058

**PNG·PDF 저장에서 글자가 겹치는 문제를 어떻게 잡을 것인가**

`CONFIRMED` — **공용 캡처 모듈 + 글꼴 대기 + 2회 렌더 + 크기 고정.** 2026-08-23 사용자 보고.

### 증상

저장한 PNG·PDF에서 글자가 서로 겹쳐 찍혔습니다.

```
화면:  D  동료와 생각을 정리하는 방식
          몰입형

저장:  D  동료와 생각을
          몰입형는 방식      ← "몰입형"이 "정리하는 방식" 위에 겹침
```

### 원인

`html-to-image`는 DOM을 SVG `<foreignObject>`에 넣어 **브라우저에게 다시 그리게** 합니다.
이때 글꼴이 아직 준비되지 않았으면 **대체 글꼴의 글자 폭으로 줄을 나눈 뒤,
준비된 진짜 글꼴로 글자를 그립니다.** 배치와 그리기가 서로 다른 글꼴을 보게 되어
줄이 겹치고 상자 밖으로 삐져나옵니다.

`getFontEmbedCSS`로 글꼴을 심고는 있었지만, **심은 글꼴이 실제로 물릴 때까지 기다리지 않았습니다.**

이 검사는 `font-display: block`으로 글꼴을 불러오고(DEC-035), `next/font`가
metric override가 붙은 대체 face를 함께 만듭니다. 두 조건이 겹쳐 어긋남이 크게 드러났습니다.

### 확정 내용

`src/features/result/captureNode.ts` 하나로 모으고 세 가지를 지킵니다.

| | 하는 일 | 왜 |
|---|---|---|
| ① `document.fonts.ready` | 문서 글꼴이 준비된 뒤 시작 | 준비 전에 재면 화면과 다른 폭으로 줄이 나뉩니다 |
| ② **두 번 그리기** | 첫 결과는 버리고 두 번째를 씀 | 첫 번째에 SVG 안의 글꼴이 실제로 물립니다 |
| ③ 폭·높이 고정 | `getBoundingClientRect()` 값을 올림해 전달 | 안 넘기면 foreignObject가 다른 폭으로 줄을 다시 나눕니다 |

올림(`Math.ceil`)인 이유: 내림하면 마지막 줄이 1px 잘려 글자가 깎여 보입니다.

### 함께 정리한 것

PNG 저장과 PDF 저장이 **각자 캡처 코드를 들고** 있었습니다. 옵션이 조금씩 달랐고
글꼴 캐시도 둘로 나뉘어, 한쪽만 고치면 다른 쪽은 계속 깨지는 구조였습니다.
공용 모듈로 합치고 글꼴 캐시도 하나로 만들었습니다 — 첫 저장만 느리고 이후는 즉시 끝납니다.

### 회귀 방지

`captureNode.test.ts` 8개. 브라우저 없이 래스터 결과를 볼 수는 없으므로 **절차**를 지킵니다.

- 글꼴 준비를 기다렸는가
- 두 번 그리고 **두 번째**를 돌려주는가
- 두 번 모두 **같은 옵션**을 쓰는가 (다르면 배치와 그리기가 또 어긋납니다)
- 크기를 올림해 못 박았는가
- 글꼴 CSS를 한 번만 만드는가

## DEC-059

**사용자가 알고 있는 실제 코드를 교직 환산 코드와 어떻게 비교할 것인가**

## DEC-062

**결과 페이지의 분량과 문장을 어떻게 줄이고 다듬을 것인가**

`CONFIRMED` — **요약 보기를 기본값으로 두고 자세히 보기를 탭으로 분리, 중복 3종 제거, 결과 문장 1차 재작성.** 2026-08-23 사용자 승인.

### 배경

한 사람이 결과에서 읽는 분량이 **약 2,000자 · 카드 25장 · 그림 3종**이었습니다. 검사 자체가 5분인데
결과 읽기가 그보다 길었고, 그중 약 300자는 **같은 문장을 두 번 읽는** 것이었습니다.

### 결정 내용

**1. 요약 보기 / 자세히 보기 (Q1-A · Q2-C)**

- Hero(제목·4렌즈 코드·교직 리듬·캐릭터·밸런스 지도)는 탭 밖에 그대로 둡니다.
- 그 아래를 `요약 보기`(기본) / `자세히 보기` 두 갈래로 나눕니다. Base UI `tabs`를 씁니다(새 의존성 없음).
- 요약은 **새 해석을 만들지 않습니다.** 관점 네 장(제목+막대)과 각 묶음의 첫 항목만 씁니다.
- 고르지 않은 갈래도 DOM에 남깁니다(`keepMounted`). 전환할 때 카드와 차트를 다시 만들지 않아 즉시 바뀌고 스크롤이 튀지 않습니다. 숨김은 `hidden` 속성이라 화면·브라우저 찾기에서는 보이지 않습니다.
- 선택은 주소의 `?view=detail`에 남겨 새로고침·링크 공유에도 유지합니다.

**2. 중복 제거 (Q3)**

| 무엇 | 이전 | 이후 |
|---|---|---|
| 축 서술 | Hero 렌즈 카드 4장 + 관점 카드 4장이 같은 headline·summary를 반복 | **관점 카드 한 곳**으로 통합(글자·극 이름·도드라짐 배지도 이 카드로) |
| 같은 점수의 그림 | 4렌즈 글자 · 밸런스 지도 · 발산 막대 | 지도는 Hero, 막대는 관점 카드로 자리를 나눔 |
| 두 관점 해석 | 최대 6장(약 400자) | **기울기가 큰 축이 들어간 2장** |

**3. 문장 1차 재작성 (Q6)**

- 축 서술 44개의 `rhythm`을 **장면 예시 한 문장**으로 바꿨습니다. 이전에는 headline·summary와
  같은 말을 문어체로 되풀이해, 같은 사실을 세 번 읽게 했습니다.
- 쓰이지 않게 된 `emphasisTerms` 8개를 정리했습니다.

**4. 협업 문구에서 분류 라벨 제거 (Q4)**

- `몰입형과는, …` → `혼자 정리하는 동료와는, …` 형태로 64개를 풀어썼습니다.
  결과 본문에서 `~형`을 되짚게 하지 않습니다. 회귀 테스트도 `동료와는`을 요구하도록 바꿨습니다.

**5. 균형일 때의 제목 (Q5)**

- **문서에 맞춰 코드를 고쳤습니다.** 균형 축이 하나라도 있으면 `resultNarrative.balancedTitle`을 씁니다.
- 이유: 균형 축의 방향은 `axis.defaultPole`이 임의로 채웁니다. 그 부호로 고른 16개 프로필의 제목을
  그대로 쓰면 동전 던지기로 정해진 이름을 "당신"이라고 부르게 됩니다. 장면·협업·행동 문구는 이미
  균형 전용 안내로 바뀌고 있었는데 제목만 유형 이름이라 같은 화면에서 앞뒤가 어긋나 있었습니다.
- 균형 전용 리듬(`balancedRhythm`)을 콘텐츠에 새로 두었습니다. 없으면 프로필 리듬으로 되돌아갑니다.

**6. 결과 문장 2·3차 재작성 (2026-08-23 추가)**

1차(축 서술의 `rhythm`)만으로는 부족했습니다. `앞으로의 흐름을 먼저 그린 장면이 있는 편`처럼
**제목 자체가 읽히지 않는다**는 지적을 받아 아래까지 넓혔습니다.

| 무엇 | 이전 | 이후 |
|---|---|---|
| 강도 사다리 | 어떤 장면 / 여러 장면 / 장면이 바뀌어도 / 대부분의 장면 | **가끔 / 자주 / 상황이 달라져도 / 거의 늘** |
| 축 서술 제목 | 명사구 — `~한 장면이 있는 편` | 짧은 평서문 — `가끔 말하다가 생각이 풀려요` |
| 축 서술 본문 | 추상어 | 교실에서 쓰는 말 |
| 화면 고정 문구 | `장면에 따라 달라지는 점`, `두 관점이 함께 드러나는 장면` | `상황에 따라 달라지는 점`, `두 관점이 겹칠 때` |
| 협업·행동·질문 | `판단 근거를 나누기 쉬워요`, `확인 시점`, `지원 판단` | `왜 그렇게 정했는지 나누기 쉬워요`, `언제 확인할지`, `누구를 어떻게 도울지` |

- 축 서술 132문장(제목·본문·장면 예시), 장면 서술 29곳, 협업·행동·질문 108곳, 조합 해석 7곳을 고쳤습니다.
- `emphasisTerms`는 새 본문에 맞춰 40개로 다시 짰습니다. 목록과 본문이 어긋나면 테스트가 잡습니다.
- **'장면'은 장면 태그(수업·생활지도·업무·동료·학부모)에만 남깁니다.** 그 다섯 개는 구체적인 자리 이름이라
  읽는 데 걸리지 않습니다.

### 하지 않은 것

- 요약 전용 문단을 16유형에 새로 쓰지 않았습니다. Hero의 교직 리듬 세 문장이 이미 그 자리를 맡고
  있어, 문단을 하나 더 두면 같은 말을 두 번 읽게 됩니다. 대신 `oneLiner` 16개는 화면 어디에도
  쓰이지 않는 상태로 남아 있습니다 — 되살릴지 지울지는 다음 결정으로 남깁니다.
- 문장 2차(장면 153개)·3차(협업·조합·행동 194개)는 1차를 확인한 뒤 진행합니다.

### 버전

- 문항·축·채점값은 그대로이므로 `assessmentVersion`·`scoringVersion`은 유지합니다.
- 결과 문구와 구조가 바뀌므로 `contentVersion`을 `4.3.0`으로 올립니다.
