## R-1. 유형 목록 탭 ★ 우선순위 1

16개 유형을 한자리에서 훑어보는 **별도 탭 / 라우트**입니다.

### 개요

| 항목 | 내용 |
|---|---|
| 경로 후보 | `/assessments/[slug]/types` |
| 진입점 | 결과 페이지 하단 · 검사 소개 페이지 |
| 핵심 동작 | 16유형 카드 목록 → 개별 유형 상세 |
| 내 결과 | 내 유형을 **강조 표시**하되, 없어도(미검사) 페이지가 동작해야 합니다 |

### 설계 주의점 — 우열로 읽히지 않게

이 화면은 **16개를 나란히 놓기 때문에 비교가 필연적으로 발생합니다.** 그래서 규칙이 필요합니다.

| 규칙 | 이유 |
|---|---|
| 정렬은 **고정 순서**(축 조합 순)로 둡니다 | 인기순·점수순으로 두면 즉시 서열이 됩니다 |
| 유형별 **점수·비율·인기도를 붙이지 않습니다** | `AGENTS.md` 6절 — 등급·순위 금지 |
| "희귀한 유형" 같은 표현을 쓰지 않습니다 | 희귀함이 곧 우월함으로 읽힙니다 |
| 카드 크기·색 비중을 **모두 동일하게** 합니다 | 시각적 위계가 곧 서열입니다 |
| 내 유형 강조는 **테두리·배지**로만 | 크기를 키우면 "내 것이 더 중요"가 됩니다 |

### 선행 조건

- PRD Phase C 완료 — 16유형 문구가 확정되어야 합니다
- 유형 엠블럼 16종이 모두 생성 가능해야 합니다 (`TypeEmblem`, DEC-039)
- 새 route이므로 **DEC 필요** — `AGENTS.md` 1.4 "navigation 구조 변경"

### 열어 둘 질문

- 미검사 사용자가 이 탭을 먼저 보면 검사 동기가 올라갈까, 내려갈까
- 16개를 한 화면에 다 보여줄까, 축별로 필터링할까

## R-2. 유형 비교 보기

두 유형을 나란히 놓고 차이를 봅니다. **연수에서 동료와 맞춰 보는 용도**입니다.

| 항목 | 내용 |
|---|---|
| 진입점 | R-1의 유형 상세에서 "다른 유형과 비교" |
| 보여줄 것 | 네 축 중 어디가 같고 어디가 다른가 · 함께 일할 때 이어지는 점 / 맞춰 둘 점 |
| 금지 | **"궁합"** 표현 (`AGENTS.md` 6절) · 점수화된 적합도 |

**선행 조건**: R-1 완료. `CollaborationProfile`이 유형쌍 단위로 확장되어야 하는지 먼저 판단.

## R-3. 렌즈별 탐색 페이지

PRD 4.4의 **6개 축쌍**을 각각 독립 페이지로 만듭니다. 사분면 위에 16유형을 배치하면 "이 두 축으로 보면 세상이 이렇게 나뉜다"가 보입니다.

**선행 조건**: PRD Phase C1(렌즈 6개 확장) 완료.

**주의**: 사분면 위 배치는 **위치가 곧 평가**로 읽히기 쉽습니다. 축 라벨을 양쪽 모두 중립적으로 달고, 사분면에 색 농도 차이를 주지 않습니다.

## R-4. 진짜 PDF 파일 생성

PRD 10.3에서 **인쇄 스타일 + 브라우저 인쇄**로 처리하기로 했습니다. 그래도 부족하면:

| 항목 | 내용 |
|---|---|
| 후보 | `jsPDF` · `pdf-lib` |
| 비용 | 번들 크기 증가 · 한글 폰트 임베딩 필요(Pretendard 2MB) |
| **선행 조건** | **새 dependency이므로 사용자 승인 필수** (`AGENTS.md` 1.4) |

**먼저 확인할 것**: 브라우저 인쇄로 만든 PDF의 품질이 실제로 부족한가. 부족하지 않으면 도입하지 않습니다.

## R-5. 다크 모드 차트 팔레트

DEC-021이 `WAITING` 상태입니다. 다크 모드를 도입한다면 차트 색은 **별도 작업**입니다.

> **자동 반전 금지.** 밝은 배경용 팔레트를 뒤집으면 대비와 색약 분리가 모두 깨집니다.
> 어두운 표면 기준으로 **각 슬롯을 다시 고르고 다시 검증**해야 합니다.

```bash
node scripts/validate_palette.js "<hex,…>" --mode dark --surface "<dark-surface-hex>" --pairs all
```

**선행 조건**: DEC-021 확정.

## R-6. 결과 검증 (DEC-046 C 단계)

PRD는 **설계값**으로 진행합니다. 실제 근거를 얻으려면:

| 단계 | 내용 |
|---|---|
| 인지 인터뷰 | 실제 교사가 문항을 어떻게 바꿔 말하고 어떤 장면을 떠올리는지 |
| 우선 검토 문항 | 유연성/미루기 · 회복/말수 · 구체성/계획성처럼 **섞일 수 있는** 문항 |
| 익명 파일럿 | 문항 분포 · 축 내 관계 · 축 사이 상관 · 축 구조 |
| 원자료 취급 | **서버로 보내지 않고 로컬에서만** (`AGENTS.md` 1.2) |

**이 단계를 마쳐야 조정할 수 있는 것**

- 강도 구간 경계 (PRD 6.1)
- S3 일관성 경계 0.8 / 1.8 (PRD 4.2)
- S4 격차 임계 1.5 · 최소 문항 3 (PRD 4.2)
- 동점 처리 규칙

> **B-2 진입 제한 유지**: 실제 인터뷰·파일럿 근거 없이 문항 교체, 점수 경계, 동점 처리를 임의 확정하지 않습니다. 변경하려면 **별도 DEC와 사용자 승인**이 필요합니다.

상세 절차는 `docs/content/teacher-style-v1-validation.md`를 따릅니다.

## R-7. 두 번째 검사 추가

플랫폼 구조의 진짜 시험대입니다. `AGENTS.md` 7절 기준을 만족하는지 확인하는 용도로도 가치가 있습니다.

```
만드는 것    src/infrastructure/content/packages/<검사id>/ 폴더 하나
고치는 것    StaticAssessmentCatalog.ts 한 줄
고치지 않는 것  domain/ application/ features/ app/ components/ui/ — 0줄
```

> PRD v2에서 `signals.ts`를 추가하면서 **이 조건이 여전히 성립하는지** 확인해야 합니다.
> 신호 계산이 특정 검사의 맥락 태그 종류에 묶이면 엔진이 콘텐츠에 오염된 것입니다.
> → 맥락 종류는 **콘텐츠가 소유**하고 엔진은 문자열로만 다뤄야 합니다 (DEC-004와 같은 원칙).
